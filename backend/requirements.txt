# Verrou des dépendances d'exécution du backend — résolution Linux / CPython 3.12.
#
# `pyproject.toml` reste la déclaration de ce dont l'application a besoin ; ce fichier-ci n'est
# que le résultat figé de sa résolution. Les contraintes du pyproject ne sont que des planchers
# (`>=`) : deux constructions du même commit à quelques semaines d'écart n'installent pas les
# mêmes bibliothèques, donc ne produisent pas la même application.
#
# Le nom `requirements.txt` n'est pas décoratif : c'est celui que pip-audit et Dependabot savent
# lire. Un `.lock` serait ignoré par les deux, et la CI signalerait des CVE que rien ne
# corrigerait.
#
# Les versions ci-dessous sont celles contre lesquelles la suite de tests passe (elles ont été
# relevées dans `backend/.venv`, puis re-résolues sous Linux pour obtenir les bonnes roues
# binaires) — pas la résolution la plus récente du jour. Une mise à jour se fait donc en deux
# temps : régénérer, puis relancer `pytest`.
#
# Régénération (dans un conteneur Linux, pour obtenir les roues binaires de la cible et non
# celles du poste de développement) :
#   cd backend && docker run --rm -v "$PWD:/src:ro" python:3.12-slim \
#     sh -c 'pip install --quiet /src && pip freeze --exclude-editable' \
#     | grep -v '^renovation-plan-backend'
#
# Les extras de développement (pytest, ruff, mypy…) n'y figurent pas : ils n'entrent pas dans
# l'image de production. L'étage `dev` du Dockerfile les ajoute par-dessus ce verrou.
